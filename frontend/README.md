# 前端 F00–F20：食材库、单据审核与价格分析

界面文案面向采购和审核人员：只展示他们看得懂、用得上的信息。接口地址、内部字段名、记录 ID、原始服务端说明和全为 0 的统计项只留在开发文档，不直接显示在页面。

本工程是 uni-app、Vue 3、TypeScript 的 H5 起点。`src/pages.json` 只注册一个业务页面 `src/pages/workspace/index.vue`。食材维护与选择器、单据列表/详情/单据头编辑、图片与 PDF 上传、补传、识别任务状态、原件预览与字段证据、逐行草稿编辑、食材匹配、逐行状态及整单收口已接入真实接口。

审核行会根据服务端的 `food_item_match` 说明食材是由历史描述匹配、商品名识别还是系统新建而选中。首次录入而库里没有同名食材时，审核页可核对食材名称、中文翻译并选择分类（可就地新建分类）；同一商品行含中英文时先拆分展示，确认入账时才建食材，首个单位取本行采购单位。手写件仍由用户核对原件；所有行仍须人工点击确认才能入账。

审核行的「查找食材建议」使用 `/api/food-items/suggest`：输入名称查模糊候选，清空输入看最近与常用；候选列出匹配依据、分数和采购历史，旧名称合并后会指向当前食材。食材库列表继续使用确定性搜索 `/api/food-items`（F17）。

## 本地启动（PowerShell）

先在项目的 `backend/` 目录执行：

```powershell
python -m pip install -r requirements.txt
python -m alembic upgrade head
python app.py
```

Flask 默认监听 `http://127.0.0.1:5000`。迁移和启动应从 `backend/` 执行；具体配置见 [后端 README](../backend/README.md)。另开终端，在 `frontend/` 目录执行：

```powershell
npm.cmd ci
npm.cmd run dev:h5
```

浏览器访问 `http://127.0.0.1:5173/`。PowerShell 若允许 `npm` 脚本，也可将 `npm.cmd` 写作 `npm`。Vite 将同源 `/health` 和 `/api` 请求代理至本机 Flask；请不要把浏览器请求直接改为跨域的 `:5000` 地址。检查类型与发布构建分别运行 `npm.cmd run typecheck`、`npm.cmd run build:h5`，构建输出在 `dist/build/h5/`。

页面在同一 URL 下用 `?view=invoices`、`?view=batch&batch=123`、`?view=organize&batch=123`、`?view=ledger&batch=123`、`?view=ingredients`、`?view=ingredients&tab=prices&food_item=123` 或 `?view=review&invoice=123` 恢复视图；ID 只接受正整数。首页只有一个**「上传单据」**入口（第 11 节 ①），可一次选择图片、PDF、CSV、XLSX。**选到的只有一份单据时**——一张图片，或本地数到只有一页的 PDF——直接进入填写页，不出现整理界面；其余情况（多份文件、多页 PDF、表格）进批次和整理页。⚠️ 页数在**本地**用 pdf.js 数，数不出来时一律走批次：整理页能处理一份文件，单张路径却会把一叠发票并成一张。「接着整理」与单据列表中的入口可恢复最近的开放批次，批次页的绿色主按钮「开始填表」进入整理页（第 22 节 ③；2026-11-24 前叫「按日期和商家整理」）；旧表格单独导入仍在单据列表。食材列表的「分类管理」旁是「价格」入口，列表中原先独立的「选择食材」弹窗已移除；价格页可返回食材列表。各业务页左上角可返回首页。旧的 `?view=prices` 链接仍进入价格页。浏览器前进、后退和刷新保留已选视图。App 系统返回键尚待平台适配与真机验证。

## 混合文件整理批次（M09）

**两个标题上都不写批次号**（2026-11-24 反馈，第 19 节）：上传页叫「上传单据」（与首页入口、整理页的「返回上传」同名），整理页叫「按日期和商家整理」。`intake_batches.id` 是库里的主键，而界面上从来没有「在几个批次里挑一个」——要么是刚传完的这一批，要么是首页「接着整理」打开的 `/current`。它仍然在 URL（`?view=organize&batch=2`，刷新和换设备靠它恢复）、接口、日志和标题元素的 `data-batch-id` 上。

批次页逐份上传图片/PDF 到 `/api/intake-batches/{id}/files`，显示真实上传字节进度；CSV/XLSX 先用现有表格映射界面预览，再传到同批次的 `/spreadsheets`。文件处理只显示 `pending/ready/failed` 的实际状态、内容数和失败原因，不把切页状态换算成百分比。坏文件不阻止其它文件；刷新、从单据列表回来或在另一浏览器打开 `?view=batch&batch=<id>`，会从服务端重读已保存文件。中断时还没传成功的本地文件需要重新选择；批次原件可下载核对。每一行写着大小、处理状态、切出几项和**传入时刻**（按本机时区，两份同名文件靠它分得开）。**传错的文件在这里就地「移除」**，按钮是红的：这一步**真的会删**——它切出的内容与做过的日期/商家分类一起没了，重新上传当作全新的一份（第 16 节）。确认在对话框里问一次，成功后那一条在原地写明删掉了几项，本次选择里对应的那条也一并撤掉。文件已有内容进入填表时「移除」按钮**暗着**，按钮上方同时写出原因（手机上没有悬停，不能只靠 `title`）。

整理上传不会创建采购记录。本页只负责上传和恢复，上传完点**绿色的「开始填表」**进入 M10 的卡片整理页（第 22 节 ③；「继续选择文件」同时退成白色——文件传完了之后，这一页上要做的下一件事是填表）；财务表格视图是 M11，整条链路到价格历史在 M12 已用隔离库与 Edge 无头浏览器实跑验过：合成文件那一轮用 Fake 识别器，另有一轮用**真实识别器**跑 3 份真实原件，一路走到价格历史。H5 已用隔离库和 Edge 无头浏览器验证；App 的混合文件选择和真机操作仍未验收。

## 按日期和商家整理（M10）

整理页在 `?view=organize&batch=<id>`，从批次上传页的「开始填表」进入，也可以直接打开这个地址恢复。左边是「待归类」卡片，右边按「日期 → 商家」摆出目标组；日期标题下的「商家待定」就是只定了日期的那一组。右边会直接显示可用的系统建议组，建议仍与人工确认区别标记。日期标题可手动新建：日期填在**年 - 月 - 日三个固定格子**里，分隔线已经摆好，只填数字，`6` 自动补成 `06`（第 11 节 ②；「移到…」面板的「其它日期」和整组「修改日期」用的是同一个控件）。最后一项移走后空日期仍保留，只有点「删除类别」才消失。

页头只留**做得了的事**（第 18 节 ①②）：工具栏是「返回上传 / 刷新 / 开始·继续识别」，加上有东西可撤时才出现的「撤销上一步」；**「重试识别失败项」只在真有失败项时出现**并写出有几项（按 `missing=recognition_failed` 的 `total` 判断，不数页面上已加载的卡片——收起来的组里那几项数不到）。说明文字只剩「点『开始/继续识别』……」那一行，其余两段讲的是界面自己就能说明白的事。

卡片上三件事分开显示：实心绿标是**人工已确认**的日期/商家，虚线框是**系统建议**并写明依据（纸面读出、参考同文件、与历史写法相近、与历史单据外观相似），另有「缺日期」「缺商家」和一句识别说明。识别说明区分「还没读这张纸」「读过了，纸面上没找到商家」「纸面日期按月/日/年读作 X」「读取失败」，不把四种情况都写成「未知」。⚠️ 日/月顺序定不死时按本项目默认的月/日/年读（第 15 节），卡片写的是**依据**而不是「要人工确认」——`6/3` 在这批纸上就是 6 月 3 日，再问一次只是把系统的犹豫转嫁给用户；值仍然是建议，可在右侧改。Fake 识别的内容带「演示识别结果」标记。

归类有三条入口，**都发同一条后端命令** `POST /api/intake-batches/{id}/moves`：

- **拖拽（桌面快捷方式）**：按住卡片右侧的手柄拖动，拖到某一天的区块里只写日期，拖到商家组同时写日期和商家。⚠️ **整块日期区都是「只定这一天」的投放目标**（第 17 节 ②），不只是标题那一条——用户说的「拖到 Day1 里面」指的就是这一整块；里面的商家组各有自己的投放目标，所以放到某一家头上仍然是两项一起定。拖动时目标区高亮，多选时预览显示张数，`Esc` 取消；指针停在视口上下边缘时页面继续滚动，以便拖到屏幕外的组。
- **放进别人家的组会先问一句**（第 17 节 ②）：卡片自己已经有商家（人定的，或纸面读出的）而目标组是另一家时，弹出的对话框给两条路——「只改日期，保留原商家」（它会在那一天下面**自成一组**）或「改成〈那一家〉」。以前这一下是静默覆盖：一张 KUN KEE 的纸拖进 NEW MOY'S 组就被写成 NEW MOY'S，之后再怎么改日期都跟着错。
- **点选 + 点目标组**：选中若干张，再点某个组的「移入所选」或日期标题的「只定这一天」。按钮是键盘可达的，Enter 即可完成与拖拽等价的操作。
- **「移到…」面板**：选中内容后从底部操作条或卡片的「更多」打开，列出本批已有的日期和商家，日期没列出时用年-月-日三格填写，商家可留「商家待定」或填新名字。

每次移动后顶部出现「已把 N 项移到…」并附「撤销这一步」，撤销走服务端的 `moves/{id}/undo`，只能撤最近一次。另一个会话先改了同一张内容时，这边会收到「内容版本已改变」的提示、**整批移动一项都不生效**，页面随即重读服务端结果；不是版本冲突的失败会保留同一个 `request_key` 供「重试这一步」，所以重试不会移动两次。

桌面整理页的待归类栏在长页面滚动时停留在视口内，栏内内容过多时独立滚动。窄屏（约 390px）同时显示日期分组和浮动待归类贴片：贴片随页面滚动留在屏幕里，长按顶部「长按移动」可换位置，卡片右侧的拖动手柄仍可拖到目标组。点「收起」后，普通页面位置留下「展开待归类」入口；点它可重新展开。点选内容后直接点目标组也能完成归类，不依赖拖拽。手柄只有自己那一小块 `touch-action: none`，所以手指按在卡片正文上仍然能滚动；原件预览里的翻页、缩放和滚动也不会被拖拽抢走。

点卡片正文打开原件预览：图片直接显示，PDF 用现有查看器翻页和缩放，CSV/XLSX 的行按现有行为提示下载原件核对。整理仍然不产生采购记录。

**开始填表**：只填一份时，点**那张卡片上**的「开始填表」（绿色，在「拖动」左边；第 13 节 ⑤）——单份不必先勾选，它也不会动你在别处勾上的东西。要把几份合成一张单据，勾选同一天、同一商家的内容后点组上的**「勾选多个文件填表」**（第 13 节 ⑥）；勾选跨了日期或来源时这个按钮是暗的，悬停显示「无法同时入库来自不同日期或者不同来源的文件。」。**单据边界只认纸面单号**：单号相同的页留在同一草稿，**读不出单号的页一页一张**（第 12 节）；页面顶部可在本次草稿之间切换。同一个文件里挨着不能证明是同一张发票——一份 PDF 本来就是几十张独立发票扫在一起的。合错了两张发票的金额会相加，而「各行之和对不上单据总额」这个检查正好因此失效；拆错了在填表页的「原件文件」里勾选页码就能并回去（见 F04 的拆分 / 合并）。填表页的 PDF 查看器只允许翻到该草稿选中的页。不同日期或商家、页与表格行混选、已在填表中的内容都会被拒绝。填完一张单据收口后回到整理页，整批单据可以在这一页里走完，不必绕去单据库——整理页的工具栏也不再有「单据列表」按钮（第 11 节 ⑤）。⚠️ 「回哪里」由**这张单据自己**说了算（第 22 节 ①）：只要它的 `intake_sources` 指向那个还开着的批次，填完就回整理页——刷新过、或者从单据库点进来接着填的那一张也一样。以前这一点只看内存里的「从哪进来的」，刷新一下就被丢回单据库。

**整批填完了：最后一组下面的「确认完成所有填写」**（第 22 节 ②）。它是这一批的终点：点一下调 `closeIntakeBatch`，批次收口，页面落到单据库的「已完成」，首页那个「接着整理」因为 `/current` 成了 404 而消失。还剩项没填完时它**自己暗着**并在旁边写出「还有 N 项没有填完」（同第 13 节 ⑥ 的口径，不是点下去才被拒）；那个 N 来自批次详情的 `unfinished_item_count`，**不是数页面上的卡片**——整理页只加载展开了的那几组。⚠️ 没有确认对话框：按得动的时候这一批已经一项不剩，收口不删任何东西。用不上的文件请在上传页移除（第 16 节），否则它们会一直算在「还没填完」里。整理页的「移回待归类」会记住人工清空决定，系统建议不会立即把它移回原组。

若浏览器连接到尚未重启的旧后端，批次详情可能缺少上述两个计数字段。整理页此时会分页读取该批次全部内容，按各项 `review_status` 计算总数和未完成数；核对前按钮保持禁用并显示「正在核对」，读取失败也不会把未知当成 0。2026-11-24 的本机批次 #2 曾因此误显示「这一批还没有可整理的内容」：旧服务响应没有计数字段，但内容接口有 5 项且全为 `completed`。重启 5000 服务后，批次详情返回 `item_count=5`、`unfinished_item_count=0`。

卡片左边的勾选框**点击区仍是 44px，看得见的方框只有 22px**（第 13 节 ④）：整块 44px 都画成边框时它看着像个空按钮。

**「改商家」就在卡片上**（第 17 节 ①）：组上的「修改商家」改的是整组的名字，所以一张放错商家的纸以前没有出路——人工决定压过纸面候选，而卡片上只有连日期一起要的「移到…」。现在每张还没开始填表的卡片都有「改商家」，面板里直接给出**这张纸自己读出的商家**和这一批里已有的商家，保存后只改这一张、**日期不动**。它走的仍是带版本检查与撤销记录的同一条移动命令（`action: "source"`）。

开始填表之后那几张卡片带上**「编辑中」**标记、不再给拖动手柄；再试着移动它们时页面先说清这件事，不等服务端 409。这一条靠 `/items` 上的 `handed_off_at`（M12 新透出）。

卡片「更多」里的红色「删除」先展示确认框。尚未开始填表时只删这一页或表格行；已开始填表时沿用「删除本张单据」的整单作废规则，同一草稿的关联页一起移除，已入账的采购记录作废并保留修改历史。批次填表页左上角只留「返回分类页面」，直接返回该单据所属的整理批次；单张上传仍返回单据库。

首页「接着整理」只在 `/current` 找到**有未移除文件的开放批次**时出现。空批次即使数据库状态仍是 `open`，也没有待办内容，不在首页展示。回首页会重新读取这一状态，避免刚离开空上传页时留下过期入口。

卡片上同时有两条出路（第 11 节 ③④）：**「继续填表」**按 `review_invoice_id` 直接回到那张草稿——退出填表页之后仍然找得回去；**「撤回填表」**——卡片上「继续填表」正下方的红按钮，「更多」在它右边同一行（第 13 节 ②；2026-11-24 前它藏在「更多」里，现在那里不再重复一份）——先问一句「回到待填表状态会清空这张单据已经填写的数据，是否继续？」，确认后删掉草稿和填过的行，**结果就留在这个对话框里**（第 13 节 ③：只写在页面顶上的那句，在长页面上看不见，用户会以为什么都没发生），卡片回到**分类好、还没开始填**的状态（日期和商家保留；要连分类一起清掉，再点一次「移回待归类」）。⚠️ 撤回的单位是**整张草稿**，同一张草稿里的其它页会一起回来。

**已完成的卡片标「已完成」，主按钮是蓝色的「重新填写」**（第 20 节；2026-11-24 前它标「已入库」、只有一个绿色的「查看单据」，想重填得自己去单据里逐行撤销确认）。点它先问「确认清空数据，重新填写吗？」，确认后调 `refillIntakeForm`：这张单据填过的行清空、**已经入账的采购记录一并撤销**（不撤就会重复记价），日期和商家保留，然后**直接落进那张新的空表**——整页换掉就是反馈，所以这里没有结果对话框（撤回填表需要一个，因为撤完人还站在整理页上）。「查看单据」退到第二行，和「更多」并排：那是整理页到这张已完成单据的唯一一条路。⚠️ 财务表格那一列对已完成的行仍然只给「查看单据」，重新填写只在卡片页。

⚠️ **uni-app 的 `<view>` 只转发它认识的事件**：`@click` 能收到，`@pointerdown` **不会**，而且既不报错也不警告。拖拽手柄因此由 `src/shared/platform/dragBoard.ts` 的 `attachDragHandle()` 用真实 DOM 监听绑定，组件里不出现 `PointerEvent`。

## 财务表格视图（M11）

桌面从卡片整理页**标题旁边那个「▾」**里的「财务表格形式」进入 `?view=ledger&batch=<id>`；回来的入口在同一个位置——表格页标题旁的「▾」里是「卡片整理形式」（2026-11-24 反馈，第 18 节）。⚠️ 它原来是工具栏上一个叫「财务表格」的按钮，和「刷新」「开始识别」这些**动作**挤在一排，而换一种看法不是一个动作。两种视图共用同一批次和 `/moves` 分类命令；来回切换时当前页、筛选、勾选与卡片展开位置保留，重新显示时从服务端读回已保存决定。窄屏不给这个菜单（表格留给桌面核对），提示返回卡片页，不把宽表压成难以操作的小格。

表格按服务端分页，每页最多 50 行；日期和商家可精确筛选，待定原因可筛出「缺任一项」「两项都缺」「日期缺失」「商家缺失」「仅缺其中一项」或「识别失败」。原件文件名及 PDF 页号、CSV/XLSX 原始行号始终在行上；确认值与带依据的候选分开。表格行的商品、数量和单价来自保存的解析值，数字保持原字符串，不经前端浮点计算。多选后可只改日期、只改商家、同时改两项或清空决定；版本冲突会重读并提示整批未生效，非冲突失败可沿用请求键重试，成功后可撤销。每行可打开原件或送入现有明细审核草稿；送审仍要求日期与商家已人工确认。已在填表中的行状态列显示「编辑中」、操作按钮变成「继续填表」（直接回到 `review_invoice_id` 那张草稿），批量改分类时这些行被跳过并给出提示（M12）。

## 价格历史（F19）

食材页的「价格」标签用食材建议选择器选定食材，逐条列出购买数量、总价和每单位价格。可比较的价格保留服务端的四位小数精度；单位未统一、未知单位、量纲不兼容时用简短提示说明暂不能比较，0 元赠品仍显示 0。多币种可显式按币种筛选。

**2026-11-18 调整**：当前业务按约定的食材单位录入采购，价格页不再提供箱规清单、补录、修改或删除。服务端保留已有接口与表以兼容历史数据；前端不再调用它们，也不修改既有采购记录。两条早期示例赠品使用 `case`，仍作为原始记录保留，价格页将其列为单位待统一。食材新增与编辑的基础单位继续从 `/api/prices/units` 读取。

## 周度、月度、来源与提醒（F20）

价格页默认展示「周均价」，并保留「月度均价」「采购历史」「来源比价」「涨价提醒」。周从周一开始；本周未结束时，与上周相同天数比较。周度和月度均价都按采购总金额除以总数量计算，折线遇到没有采购的时段即断开，不将缺失价格画作 0。来源比价默认查看近 12 周，可切换为近 3 个月；列表展示采购描述供人工判断规格、品质是否可比。

提醒默认按周比较，可切换按月比较。提醒按食材和币种分组，提供启用开关、提醒涨幅和只影响本次查看的临时涨幅。涨价提醒与暂时无法比较的项目分开列示；只有存在未参与比较的采购时，才显示简短原因。多币种统计须显式选币种，界面不混算。

F01 的布局截图在 [docs/f01](docs/f01/)：桌面单据、桌面审核、手机审核、桌面与手机食材。截图记录的是当时的布局占位；当前食材页面显示后端数据。

## 食材读路径（F02）

进入「食材」后读取 `GET /api/categories` 和 `GET /api/food-items`。关键词按后端基础搜索匹配英文名、中文名与规格；分类筛选与关键词组合传给后端。每页 20 条，「加载更多」沿用服务端 `offset`，切换关键词或分类时从首条重新查询。点击食材会通过 `GET /api/food-items/{id}` 打开详情。加载中、无结果、请求失败分别显示不同提示；失败后可重试。

## 食材维护与选择器（F03）

「新增食材」与详情中的「编辑食材」共用最短表单：英文名、分类、基础单位必填，中文名与规格在「更多信息」中。重复名称返回 409 时，字段旁显示服务端原因，并提供「打开已有食材」。详情中的删除需要再次确认；没有单据入库关联时，一并清理独立采购和修改历史；已有单据入库记录时服务端拒绝删除。

「分类管理」是食材页的次级入口，可新增、改名、删除分类；仍被食材引用时显示食材数量和处理办法。分类修改成功后重新读取分类与食材列表。「选择食材」打开独立的 `IngredientPicker.vue`，支持搜索和加载更多；组件只在用户点击某条结果的「选择」后发出该食材 ID，供后续审核行复用。当前页面只展示选择结果，不改动任何记录。

## 食材合并与孤立食材筛选（F18）

食材详情的「合并重复食材」固定当前食材为保留项，可搜索并选择最多 10 条被并入项。先预览服务端给出的采购记录、发票行、箱规搬动数量与冲突；确认按钮旁显示「合并不可逆」。有箱规或单位冲突时按钮禁用，页面显示服务端原因及涉及的食材、单位或箱规 ID。执行成功后显示实际搬动数量，并重新读取食材列表和详情。合并没有撤销入口。

列表的「从没买过」使用 `GET /api/food-items?never_purchased=true`，可与关键词和分类一起筛选。已作废采购记录仍算买过；该筛选只表达采购历史，不表示是否允许删除。已有单据入库记录时，删除收到 409 并显示原因。

## 单据读路径与单据头（F04）

「单据库」`GET /api/invoices?completed=false` 显示待办，切换「已完成」改用 `completed=true`；每页 20 条，上一页/下一页使用服务端 `offset`。图标卡片按当前排序依据的月份分段：待处理按录入月份，已完成默认按单据发生月份，切换「按创建时间排序」后按录入月份。右侧时间轴从 `GET /api/invoices/months` 取得当前筛选条件下的所有月份，选中月份的线条加长；点月份可跨页定位并滚动到该月标题，日期筛选与分页仍生效。一张发票一张图标卡片：显示状态、醒目的单据发生日期、原件局部预览、来源名称与已填写的单据总金额；未填总金额时该位置留空。只有待核对行数非零时显示「待核对 N」；纸面单号、「已跳过」行数、创建日期和原件页码不在卡片上展示，完整行状态与原件出处可进详情查看。库里的 `invoices.id` **不印在卡片上**（它只用于 URL、接口和日志），但留在卡片元素的 `data-invoice-id` 上供浏览器实跑认卡片。点击「查看详情」通过 `GET /api/invoices/{id}` 查看单据头、默认展开的原件和行状态；原件可自行收起再展开。空字段按所在区域显示「待填」或留空，没有行时不伪造进度。加载中、空列表、请求失败分别提示。

H5 的离开、删除、撤销等 `uni.showModal` 提示框统一使用工作台的白色卡片、深绿文字、圆角按钮和绿色／错误色操作文字；整理页、食材选择和财务表格的浮层统一使用同一深绿遮罩。浏览器刷新或关闭标签页时仍由浏览器显示系统提示，App 原生弹窗未做真机样式验收。

**一张发票是一条记录**（第 12 节）。一次录入二十张单据就是二十条，不是一条；整理批次只是上传时的容器，整理完就没有分组意义了——同一批里混着好几天、好几家。

待处理和已完成两个页签统一以图标卡片展示，不再提供列表切换；已完成页签仍可排序和按日期筛选，两个页签仍可分页，已完成单据仍可勾选导出。卡片右上角是单据发生日期，以深色粗体突出显示（桌面 18px、窄屏 15px）。图标卡片**整体**按表格（绿）、PDF（红）、图片（紫）显示不同轮廓及类型标记，里面不再嵌套第二个文件框。PDF 缩略图仍读取单据关联的实际页，但卡片不显示页码；图片显示原件的**顶部放大局部预览**（约为整页适配的 1.85 倍，允许裁切），CSV/XLSX 显示审核行保留的原始单元格。点击缩略图进入详情查看完整原件；无法解码时显示原因。H5 图标进入可见区域后才读取原件；App 端 PDF/图片缩略图仍受现有原件预览适配能力限制。

批次仍开放时，从该批次单据返回会回分类页；点「确认完成所有填写」收口后，单据详情左上角改为「返回单据」，点击回单据库。直接打开已收口批次的卡片整理或财务表格历史链接也会转到单据库；已收口分类页不再作为导航目标。

**两个页签回答两个不同的问题，排序和筛选因此不同：**

- **「待处理」是待办清单**：不筛、不给排序选项，固定 `order=created_at`（录入时间倒序）。还没做完的东西本来就该按「什么时候进来的」排队。
- **「已完成」是翻历史**，顶上三个控件：
  - **排序下拉**「按收据日期排序」（默认 `order=invoice_date`，日期待填排最前）／「按创建时间排序」（`order=created_at`）。两者差别是实打实的：六月一日补录一张五月二十二日的单子，按收据日期排在五月，按创建时间排在最前。创建时间取响应里的 `uploaded_at`（即 `invoices.created_at`），**没有加列**；它是这条记录建出来的时刻，批次来的单据是点「开始填表」那一刻。
  - **「选定时间范围」**：点开是起止两格日期，留空一端表示那一端不限，按钮上回显当前范围，对应 `date_from` / `date_to`。按**单据上的采购日期**筛，不是录入时间；区间排除没有日期的单据。

没有「日期待填」筛选：收口确认强制要求日期，已完成的单据都有日期，这个按钮在这里永远是空的。要找没填日期的单据得去「待处理」页签。

⚠️ **原件数不能只数 `files`**：批次来的单据，原件挂在 `intake_sources`（整理内容）上，`files` 是空的。卡片显示的是真实出处，例如「four.pdf 第 3 页」或「four.pdf 2 页」。

「单据信息」始终展开，放在「完成单据」上方。来源、单号、日期、币种和总额中，识别出的值先以灰字显示，逐项点「此数据正确」或「修改」；确认和修改都会保存审核结果，重新打开仍能看见。空白字段可直接填写。日期为完成单据的必填项。总额旁的「计算总额」会取服务端已确认明细的合计填入表单，仍需保存；币种混合时不计算。清空字段会提交 `null`，金额作为字符串提交。已确认行的历史采购值不会随着单据头修改而回溯。浏览器刷新 `?view=review&invoice=<id>` 会重新读取同一单据。行草稿编辑见下面的 F07 一节；整单对账与「完成单据」见 F09。

**拆分 / 合并（填表期修正单据边界）。** 批次来的草稿在「原件文件」里逐页列出，可勾选：勾一部分点「拆出选中的 N 页」会新建一张草稿，或在下拉里选同一天、同一商家的另一张待填草稿「整张并过去」（本草稿随即作废，界面跳到目标草稿）。两者都走 `POST /api/intake-batches/{id}/reviews/{invoice_id}/reassign`。⚠️ 搬完之后**两边的单据总额都会被清空**：拆开的两半各自该是多少只有纸面知道，服务端绝不拿一个总额去除。已经入账的行搬不动，那条路是撤销确认。

**未保存就离开会先问。** 单据头编辑中改过值、上传队列里有没传完的文件、上传正在进行时，切换一级入口、返回列表、浏览器前进/后退都会先弹确认；选择「仍要离开」才丢弃，选择「留在本页」会把视图和输入留在原处。刷新或关闭标签页由浏览器自己的 `beforeunload` 提示。这些逻辑集中在 `src/shared/platform/leaveGuard.ts`，业务组件只注册「我现在有未保存的内容，原因是什么」。

## 文件上传与识别任务（F05）

「上传单据」提供三个入口：**拍照**（`uni.chooseImage` + `sourceType: ['camera']`，手机浏览器直接调相机）、**相册 / 图片**、**PDF / 图片文件**（`uni.chooseFile`）。另有开关「只保存文件，手工录入」——只存原件、不启动识别。表格（CSV / XLSX）从列表的「导入表格 / 导出明细」进入。

上传按第 4.1 节的顺序发请求，这是产品决定而不是实现方便：

1. 第一个文件 `POST /api/invoices` 且带 `recognize=false`；
2. 其余文件逐个 `POST /api/invoices/{id}/files`；
3. **全部页都存好之后**，非手工路径才 `POST /api/invoices/{id}/extraction`。

用 `recognize=true` 直接上传会让后端在第 2 页还没传完时就开始识别第 1 页——模型读了两页单据里的一页，而界面上没有任何地方会说出这件事。

选择之后、上传之前可以看到文件名、大小、页序，并用「上移 / 下移 / 移除」调整顺序；页序就是列表顺序。不支持的扩展名、空文件、超过 20 MB 的文件在本地就被拦住并说明原因，但**真正的上限由服务端决定**（`UPLOAD_MAX_BYTES`，默认 20 MB，整次请求是它的 4 倍）：服务端拒绝时照它的原文显示。超大的上传常常表现为连接被断开而收不到 413 响应，这种情况的文案会同时写出两种可能的原因，不单方面说成「后端没启动」。完全相同的文件返回 409，页面照服务端原文提示它已经在哪张单据上；跳过去打开那张单据属于 F10。

中途失败不丢已传的页：提示会写明「单据 #N 已经建立、前 K 页已保存、识别没有启动」，并给出「重试剩下的页」和「打开这张单据」。在详情里「补传文件」可以继续传，补齐后由用户点「开始识别」。上传进度是 `uni.uploadFile` 的真实字节进度，不是估算；上传中可以「中断上传」，已保存的页仍留在单据上。

**接受识别出来的金额时会先规范写法（M12）**：纸上印的是 `$1,040.00`，而金额框只收 `1040.00`，
所以点「此数据正确」时会去掉货币符号、空格和千分位逗号。去不干净的写法（例如欧式的 `1.040,00`）
原样留着，让字段原有的报错照常出现——这里宁可让人自己决定，也不替人猜一个金额。手动输入的规则没变：
校验仍然要求半角数字。这条是真实 OCR 实跑时发现的：照单收下纸面原文会让单据头存不进去，
而之后每一行的确认都会被挡在「请先检查并保存单据信息」上。

详情里的「识别任务」卡片读 `GET /api/invoices/{id}/extraction`，显示 `排队中 / 识别中 / 已完成（产出 N 行）/ 失败（原因）`。任务状态在后端持久化，所以**离开这张单据时轮询会停**，回来重新查询；任务结束后自动重读单据，草稿行随之出现。**不显示伪造的百分比**——后端给的是状态与页数，用它编一个进度条就是编数字。provider、models、`prompt_sha12`、`doc_class`、错误码和后端的全部警告收在「诊断详情」里。Fake 识别器的结果一律带「演示识别结果」标识。HEIC 可以上传保存，页面会说明预览与识别能力取决于后端和浏览器当前的支持情况，不替它们承诺。

文件选择与上传隔离在 `src/shared/platform/filePicker.ts` 与 `upload.ts`。两处 App 待办写在代码里：`uni.chooseFile` **没有 App 实现**（App 端调用会得到一句明确的错误，而不是静默失败），`uni.uploadFile` 在 App 端走 `filePath` 而不是 `File` 对象。

## 原件预览与字段证据（F06）

单据详情变成**审核布局**：桌面左边原件约 45%、右边单据头/行/证据约 55%，两侧各自滚动，切换行不会把原件滚回顶部；窄屏是「原件 / 填写」两个标签，**两块都留在 DOM 里**（`v-show`），所以来回切换保留当前行、文件、页码、缩放和滚动位置。布局用的是 JS 测到的视口宽度（`src/shared/platform/viewport.ts`），不是 CSS 媒体查询单独判断——两边各自判断会在断点附近打架，表现是桌面上少了一块。

**原件**读 `GET /api/invoices/{id}/files/{file_id}/content`，拿到的是**存进去的原始字节**，页面只做缩放，不重新编码。多个文件有文件标签，PDF 有翻页，缩放是 1× / 1.5× / 2× / 3× / 4×（PDF 会按倍数重新渲染保持清晰，图片用 CSS 放大）。选中某一行时，按它证据里的 `file_id` 与 `page` 自动跳到对应的文件和页。M08 批次送审草稿另从详情的 `intake_sources` 取得批次、内容与页/行号；查看器使用 `GET /api/intake-batches/{batch_id}/items/{item_id}/original` 读取同一份原始字节并跳到对应 PDF 页，表格可下载原件。审核头部修改这类草稿的日期/来源时，界面明确显示整张草稿的影响范围，并调用批次审核分类接口同步内容决定与沿用头值的采购；旧单张草稿仍走原接口。M09—M12 的浏览器闭环已在隔离环境实跑两轮：一轮用合成文件加仓库现有真实原件、Fake 识别器；一轮用**真实识别器**（`OCR_PROVIDER=dashscope`）跑 3 份真实原件，从混合上传一路做到价格历史回查——草稿里的明细行就是模型读出来的，在审核页逐字段按「此数据正确」接受。⚠️ 识别**准确率**是分层报告的事，见后端 README 与 `backend/docs/multifiles.md` 的 M12 记录，不由这条链路的通过与否背书。

**字段证据**按 `raw_fields` 显示五个字段的原文、识别状态（识别出内容 / 这一格认不出 / 单据上没有这一格）、各模型读法与交叉裁决结论。点字段才去取 `GET .../lines/{line_id}/crop?field=...` 的原图小块，并且：

- **后端记了坐标**（`raw_fields.fields.<字段>.box` 非空）才自动请求，**不带** `row` / `column`；
- `box_source=grid_row` 的裁图标成「**整行参考**」，明说只锚定到行、没有定位到列；
- **没有坐标就不请求**，写明「这一页没有建立行号锚定，系统不会替你猜是哪一格——请在左侧原件上核对」。页面上有「自己指定格子」，用户显式选了行带与列带之后才带 `row` / `column` 请求，并标注「这是你指定的格子……不是系统判断的位置」。猜一个 `row` 会让后端返回 200 和**相邻那一行**的字迹，这是唯一一种不报错的错；
- 裁图失败（含 404）照服务端原文显示，并说明已回退到整页原件，不显示可能错行的图片。

手工加的行没有识别证据，直接说明；表格导入的行给单元格坐标，不给原图小块（`.csv` 里没有像素）。`recognition.is_fake` 为真时原件区和证据卡都带「演示识别结果」。

**HEIC 按浏览器实际能力提示**：页面真的去解一次，解不开就说「这个浏览器解不开 HEIC……原件已经完整保存在服务端，不受影响」。有意思的是**裁图仍然能看**——后端有 `pillow-heif`，裁出来的是 PNG。

### `shared/platform/documentPreview.ts` 的边界

文件字节→可显示内容的全部浏览器 API 都在这一个文件里：`URL.createObjectURL`、`Image` 解码探测、`<canvas>` 与 pdf.js。业务组件只见到 `RenderedPage` 与 `PdfDocument`。App 端待适配的四件事写在该文件开头的表里：图片要先 `uni.saveFile` 成本地临时文件、HEIC 看系统、PDF 渲染要换平台组件或原生插件、页数同理。非 H5 分支现在抛的是一句说明缺哪项能力的错误，不是静默空白。

⚠️ **pdf.js 必须用静态 import**。`uni build -p h5`（`vite-plugin-uni` 3.0.0-alpha-5030620261106001）会把 `await import('pdfjs-dist')` 编译成裸标识符 `import("..-node_modules-pdfjs-dist-build-pdf.<hash>.js")`，而且**那个 chunk 根本没生成**：`npm run dev:h5` 一切正常，`npm run build:h5` 出来的页面直接报 `Failed to resolve module specifier`。两个 `#ifdef H5` 块负责把 pdf.js 挡在非 H5 构建之外，这正是当初想用动态 import 达到的效果。pdf.js 4.10 面向当代浏览器（用到 `Promise.withResolvers`，Chrome 119+ / Safari 17.4+）；要更宽的基线就换 `pdfjs-dist/legacy`。

## 审核草稿编辑、手工加行与食材匹配（F07）

选中一行后，审核面板里出现这一行的**草稿表单**（`src/features/invoices/LineEditor.vue`）：商品名称、数量、采购单位、单价、行金额；日期 / 来源 / 币种折在「按需覆盖」里，默认继承单据头，表单直接写出继承来的是哪个值。当前界面只录入采购行，不显示行类型切换。表单下面是**食材匹配**（`FoodItemMatcher.vue`），再下面才是 F06 的字段证据——先填，再对着左边的原件核。

**单据信息里的「来源」和别的字段长一样**（2026-11-24 反馈，第 17 节 ⑤）：绿「此来源正确」+ 红「修改」，下面**不再摊开那四行识别线索**（纸面英文名、中文名、模型摘录、模型之间读法不一致……）——那些回答的是「系统是怎么想的」，而老板要回答的是「这张纸上的商家对不对」；完整证据仍在 `raw_document_fields` 里。批次来的单据，商家在整理页已经人工确认过，所以这一对**不挂「AI 识别 · 待核对」**那个标签（说假话）；点「此来源正确」也不写库（库里已经记着它被确认过），本次打开期间再确认其它字段不会让按钮重现，刷新后会再出现一次。纸面读出的商家和当前填着的**不一样**时，上面那一行写出纸面读的是谁——整理页上的商家可能是整组带上的（第 17 节 ②），对着左边的原件复核一次正是这一页该干的事。

**批次来的单据不再顶着一张空的「识别进度」卡**（第 17 节 ③）：它没有自己的 `files`，识别在整理页就做完了，这张卡只会写一句「请先上传可识别的单据文件。」，却占着表格和原件的位置。真有任务在跑、失败或带警告时照常显示。

2026-11-17 的审核界面调整：标题与低频操作收在同一行，原件和填写区靠近视口顶部。草稿表单将「原始描述」显示为「商品名称」；可用的识别值以灰色候选放在对应空框内，未识别出的格子保持空白。一次只在当前待核对字段下显示「此数据正确 / 修改」，其他候选只在字段名旁标「AI 识别 · 待核对」；点击其输入框即可切换核对按钮。确认后候选成为可编辑的黑色表单值；修改会清掉候选并将焦点移入该框。两模型文字不一致时，候选按纯英文、纯中文、含数字或符号排序，同档取文字较多者；数字不一致时不猜。原来的两模型原文折叠区已从审核页移除。

**数字候选先按输入框的形状收一次再决定提不提**（2026-11-24 反馈，第 21 节 ①）。纸面原文带着货币符号和千分位（`$1,664.33`），而数量/单价/金额这三个框只收 `1664.33`；原来这里拿原文直接去比「纯数字」，于是**两个模型都读出来、而且读得一样**的金额被挡在外面，格子里连灰字都没有，看上去就像 AI 没读这一项。现在先 `plainAmount()` 收一次（去货币符号、千分位与全角），收得干净才提，提的就是收干净之后的值；**收不干净的照旧不提**——`-` 是纸面上真实存在的一个字符，不是数字，格子继续空着等人填。写进采购记录的数值仍然走后端的 `normalize_number_text`，这一层只管「建议值摆不摆出来」。

**行级的那个金额字段叫「金额」**（同上，第 21 节 ②；2026-11-24 前叫「行金额」）。它和「数量」「单价」并排，连起来就是纸面那一行表头（`Quantity / Price / Amount`）；单据级的那个仍叫「总额」，对应纸面的 `Total`。依据是发票的法定字段表（…单位、数量、单价、**金额**、税率、税额、合计、价税合计）、用户单据上印的 `Amount`，以及本项目 CSV 列映射界面里早就在用的「金额」。接口与数据库里的字段名仍是 `line_amount`，没有改。

四条规则是契约，不是样式偏好，都写在 `lineDraft.ts` 的注释里：

- **数值全程是字符串。** 输入、比较、提交都不经 `Number()`，也不在前端做乘除。后端的 `parse_decimal` 直接拒绝 JSON 小数，理由不是洁癖：`JSON.parse` 在任何代码读到之前就已经把 `1234567.89` 过了一遍 double。
- **空格子就是 `null`，不是 0。** 后端对认不出的格子刻意留空，而 0 在这个产品里是「赠品 / 0 元行」这种确定的含义。表单因此把两种状态分开标：空的写「未知（空）」，填了 0 的写「**这里的值是 0，不是「未知」**」。
- **PATCH 只带改过的字段，并且一定带 `version`。** 后端把「没出现的键」当成「保持原值」、把显式 `null` 当成「设为未知」；整表提交会让一份过期的表单覆盖掉别人刚改的值。`version` 省掉的话 `_check_version` 会跳过检查，于是每次保存都变成盲目覆盖。
- **候选永远只是候选。** 行自带的 `match_candidates`、`/api/invoices/{id}/supplier-candidates`、`/api/invoices/match?description=` 和 F03 的食材选择器，四个来源都只列出候选，**必须用户点一下**才会写 `food_item_id`。手写件的商品名本来就不该靠 OCR——中文商品名跨模型分歧率 96.0%，所以那条路走供应商历史：老板认的是自己的货，不是认字。

**本地校验照后端的规则写**（小数位 4/4/2、整数部分 12 位、采购行不能负数、采购行数量必须大于 0），目的是把错误提示放在字段旁边而不是等一次往返。它只会比后端更严，不会放宽；后端拒绝的一律照原文显示。

**版本冲突（409）**会重新读这张单据，然后把「你的输入 / 服务端现在的值」逐字段摆出来，给两个出口：「用服务端的值（丢弃我的输入）」和「保留我的输入，按新版本重新保存」。页面**不替用户合并**——两个数字都可能看起来成立，选错了不会报错。

**切行前会先问。** 这一行有没保存的修改时，点另一行会弹出「第 N 行改了 X，还没有保存」，只有「放弃修改」才切过去；整页离开（切一级入口、返回列表、刷新）沿用 `leaveGuard.ts`。

**加一行**：行状态概览右上角的「加一行」`POST .../lines`，所有格子先留空，加完自动选中，然后逐格填。手工加的行（`raw_fields` 为空）可以删；识别出来的行不能删——删掉就和原件对不上了，那种情况要标成「跳过」。

**首次采购自动建食材（2026-11-28 调整）**：现有食材可照常搜索选用；没有同名食材时，在确认入账前核对新食材名称、可选的中文翻译并选择分类。中英混合商品描述会按文字脚本先拆成英文主名和中文翻译，例如 `Pork Spare Rib Cube 靓排粒` → `Pork Spare Rib Cube` / `靓排粒`；这一步只拆文字，不能证明两者语义相同，用户可修改或清空中文翻译。确认时带 `new_food_item: {name, name_zh, category_id, use_purchase_unit_as_base:true}`，后端从本行采购单位取首个单位，并在同一事务内建食材、入账；入账失败不会留下孤立食材。同名已有食材复用。商品描述原文留在采购记录，供历史映射。当前录入时应填写约定的食材单位；旧包装单位记录如未统一，价格页会标明无法参与比较。已完成单据和草稿单据都可在列表标题旁重命名；改的是单据来源名称，既有采购记录的来源不会回写。

**`review_issues` 是对象数组，不是字符串数组**（`types.ts` 里原来的 `string[]` 在 F07 改掉了）。它来自 `invoice_lines.review_metadata["issues"]`，识别写的是 `field` / `code` / `raw_text` / `message`，表格导入还会加 `sheet` / `row` / `column` / `cell`。只要还剩一条，后端就拒绝确认这一行；而它只在**它自己指的那个字段被 PATCH** 之后才消失，所以每条提示就显示在那个字段旁边。

**已入账的行是只读的**：后端拒绝 PATCH 一个已确认的行，因为它的数字已经进了采购历史，原地改草稿只会让两处对不上。页面照这个口径说明，并提供「撤销确认」入口。

## 逐行状态与入账（F08）

「确认此行并入账」先保存该行尚未提交的修改，用 PATCH 返回的新 `version` 只确认这一行。确认请求显式传 `line_id`、`version` 和用户选定的 `food_item_id`。HTTP 200 仍逐条检查 `results[].ok/error`，失败会留在当前行并显示原因。金额不符时直接展示服务端返回的纸面金额、数量乘单价、差额与容差；用户点「仍按行金额入账」才带 `accept_amount_mismatch:true` 重试。金额不经前端浮点计算。

「跳过此行」必须输入原因，带 `version` PATCH 成 `skipped`；可改回待核对。已入账行的「更多操作：撤销确认」先告知原采购记录会作废，用户确认后带 `version` 调 `POST .../unconfirm`。每次状态变化从服务端更新整张单据，行计数与详情同步；「重新读取详情」可随时重查。重复确认由按钮忙碌状态与后端唯一约束双重阻止，不会多记一笔采购。

## 对账与收口（F09）

详情的「对账与漏行检查」直接显示服务端的文件数、行数、总额、已入账金额和差额。仍有待核对行、没有总额、混合币种、缺币种或币种不符时说明无法对账，不把未知差额写成 0；差额过大时提示核对，但不阻止完成。至少一行、没有待核对行且已填写单据日期，才可打开收口面板；服务端也会拒绝缺日期的完成请求。打开面板会重新读取详情；对照原件后须勾选「我已检查原件有无漏行」，才能提交 `POST /api/invoices/{id}/complete`。完成后自动切到已完成列表，单据详情仍可回看原件与已入账行。服务端 409 带 `pending_line_nos` 时会重新读取并定位未处理行。

已完成单据使用「采购回执」视图：页头显示采购来源、日期、单号和单据总额，正文以大字清单展示已入账商品，并单列已跳过的行；原件通过「查看原件」打开。右上角「修改」调用 `POST /api/invoices/{id}/reopen` 返回审核页，原有已入库行不重复入库；需要改某一行时，点「修改此行」撤销该行旧记录，修改后重新确认入库，最后再次完成单据。每条已入账行根据 `purchase_id` 读取 `GET /api/purchases/{id}`，显示当前采购记录，避免采购记录修订后继续展示过期的审核草稿。采购记录读取失败时该行不显示草稿金额，提供重试。底部的入账金额和差额明确标为**完成时**服务端对账结果；如采购记录后来修订或作废，回执会提示两者口径不同。金额和数量仍全程保留字符串，不在前端计算合计。

单据币种默认 USD，无需手动填写；审核时可在单据信息里改为 CNY，已完成回执的总额下方也可修改。已完成单据的币种修改只更改单据头，已入账采购记录不会自动换算或改币种，对账结果会随服务端响应更新。表格导入的整批币种预选 USD，可在预览前更改；表格中逐行明确写出的币种仍按行处理。已完成旧单据若未存币种，回执按 USD 默认值显示，原始记录本身不被自动改写。

## 异常恢复与低频操作（F10）

上传完全相同文件返回 409 时，上传面板可根据 `details.invoice_id` 打开已有单据；详情中的 `possible_duplicate_invoice_ids` 是提醒，可点开核对，不阻断审核。单据详情右上角只有一个 **「删除本张单据」**（2026-11-24 反馈，`backend/docs/multifiles.md` 第 17 节 ④；原来那个「单据更多操作」菜单没了），问的是「是否清空数据，并彻底移除本张单据？」，**批次来的单据连它在整理页上的那几页一起删**，删完直接回到来的地方（整理页或单据库）。重新提取、查看识别记录和删除拍坏文件搬进了下面「原件文件」那一折——它们都是对着原件做的事。重新提取会提示核对未确认草稿；运行中的任务与已入账行由后端 409 拦截。删最后一个原件、删正在识别的原件也由后端拦截。删除整单先确认；若有已入账行，再显示行数并要求二次确认。服务端核对当前行 ID，一次事务内作废其采购记录、保留修改日志，再作废单据并删除原件；已作废记录不再计入价格统计。同一文件之后可重新上传。已入账的历史数值不能通过草稿修改；当前界面尚无采购记录编辑页，需通过 `PATCH /api/purchases/{id}` 修正并保留修改日志，或撤销该行确认后重新审核。

## 表格导入与采购明细导出（F11）

在单据列表点「导入表格 / 导出明细」。选择 CSV/XLSX 后先设置工作表、表头行、列映射、编码、分隔符、数字与日期规则，再点「预览表格」。预览显示原始行号、解析值和每个异常，不写入单据。修改设置会使预览失效，须重新预览；用户确认映射与格式后才能创建。若仍有异常，须明确选择「在审核中逐行手工处理」，这些行仍不能直接确认，须在现有审核表单修正。创建后直接进入同一单据审核视图，表格原件可下载。

同一文件重复创建收到 409 后，可打开原批次；修改文件后重传会建新批次，不覆盖旧记录。导入时“行类型”列会被忽略，所有新行按采购处理。导出可选 CSV 或 XLSX；点「下载单据」后切到下方「已完成」列表，勾选单据并点「下载所选」。可跨页勾选，待处理单据不能勾选；服务端会再次核对完成状态。导出的表格只含所选单据当前有效的采购行，不含未确认、调整行或已撤销记录。App 端表格选择和下载尚待独立适配。

## Web 集成验收（F12）

在隔离 SQLite、`OCR_PROVIDER=fake` 的本地 Flask 与 Vite 同源代理上，用 Chrome 157 实际点击了 1280px 桌面和 390px 窄屏两条完整流程：新增食材、上传单据、确认两行（第二行随确认新建食材）、手工补第三行并保留待办、离开并刷新后返回、跳过第三行、完成单据、从已完成列表回看原件。Fake 识别器只生成两行，第三行通过页面的「手工加一行」补齐；界面始终标明「演示识别结果」。还在窄屏完成了 CSV 只读预览和创建，预览前后待办数不变。43 行单据在 390px 与 1280px 均无横向溢出；桌面填写区可独立滚动。另用两页合成 PDF 验证 H5 原件预览和翻页。

断网时重新读取会保留上次内容并显示失败原因；网络恢复后再点「重新读取详情」，旧错误会消失。服务端将 `UPLOAD_MAX_BYTES` 临时设为 4096 字节时，用 574 KB 图片从页面上传实际收到 HTTP 413，页面给出缩小文件的办法且未新建单据。输入框键盘焦点、Tab/Enter 主导航和空格操作收口勾选、主要文字组合的对比度、可见点击宿主的 44×44 CSS px 目标已在浏览器检查。H5 的 `uni-button` 键盘适配集中在 `src/shared/platform/keyboardButtons.ts`。此验收使用 Fake OCR；**真实 OCR 的识别效果不由本轮 Web 验收背书**。

浏览器联调发现后端在更换一行的 `food_item_id` 后，PATCH 响应仍可能带旧的 `food_item` 对象，而下一次 GET 已是新选择。前端因此在选择或取消食材的 PATCH 成功后重读单据，再显示选中项并允许确认。生产构建通过本地预览服务实测可打开两页 PDF、翻到第 2 页。

**App 真机适配清单（均未验收）**：拍照与相册权限及返回文件、PDF/表格文件选择、图片与 PDF 原件预览、表格附件下载、系统返回键和未保存提示、手机到后端的可达地址与认证及传输保护。H5 的 390px 浏览器结果不等于 App 真机结果。

## OCR 配置

后端默认 `OCR_PROVIDER=fake`：识别结果是演示数据，响应的 `recognition.is_fake` 会标出这一点。真实 OCR 需在后端本机环境中配置 `OCR_PROVIDER=dashscope`、`OCR_API_KEY`（或 `DASHSCOPE_API_KEY`）及 `OCR_BASE_URL`（或 `DASHSCOPE_BASE_URL`）；详见后端 README 的配置说明。没有真实凭据时使用 Fake 模式即可验证 F00。前端没有 OCR 密钥，也不复制后端 `.env`。

## API 基座

`src/shared/api/request.ts` 统一走 `uni.request` 和同源路径；HTTP 失败按后端的 `error.code/message/details` 解析，网络失败单独提示。`src/shared/api/types.ts` 中的金额、数量使用 `string | null`，不转换成 JavaScript `Number`。分类响应为 `{items}`；食材和单据列表为 `{items,total,limit,offset}`；提取任务为 `{items,total}`。multipart 上传走 `src/shared/platform/upload.ts`（字段名 `files`，一次一个文件）；二进制原件与裁图走 `apiRequestBinary`（`responseType: 'arraybuffer'`），裁图的证据在响应头 `X-Field` / `X-Page` / `X-Model-Values` / `X-Agreement` 里，失败时把字节当 UTF-8 JSON 解出来读服务端的 `error.code/message/details`。

⚠️ **uni-app 的一个坑记在这里**：`uni.uploadFile` 在 `@dcloudio/uni-h5@3.0.0-alpha-5030620261106001` 里，只要 `files` 不是数组就执行 `if (!filePath) reject('file error')`，**然后照样把请求发出去**——于是服务端收到并保存了文件，而调用方收到的是失败。传 `File` 对象必须用 `files: [{ name, file }]` 这种写法，`upload.ts` 的注释里也写了这件事。
