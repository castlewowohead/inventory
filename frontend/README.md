# 前端 F00–F20：食材库、单据审核与价格分析

本工程是 uni-app、Vue 3、TypeScript 的 H5 起点。`src/pages.json` 只注册一个业务页面 `src/pages/workspace/index.vue`。食材维护与选择器、单据列表/详情/单据头编辑、图片与 PDF 上传、补传、识别任务状态、原件预览与字段证据、逐行草稿编辑、食材匹配、逐行状态及整单收口已接入真实接口。

审核行会根据服务端的 `food_item_match` 说明食材是由历史描述匹配、商品名识别还是系统新建而选中。首次录入而库里没有同名食材时，审核页只需选分类（可就地新建分类）；确认入账时才自动建食材，名称取本行商品名称，首个单位取本行采购单位。手写件仍由用户核对原件；所有行仍须人工点击确认才能入账。

审核行的「查找食材建议」使用 `/api/food-items/suggest`：输入名称查模糊候选，清空输入看最近与常用；候选列出匹配依据、分数和采购历史，旧名称合并后会指向当前食材。食材库列表继续使用确定性搜索 `/api/food-items`（F17）。

## 本地启动（PowerShell）

先在项目的 `backend/` 目录执行：

```powershell
python -m pip install -r requirements.txt
python -m alembic upgrade head
python app.py
```

Flask 默认监听 `http://127.0.0.1:5000`。迁移和启动应从 `backend/` 执行；具体配置见 [后端 README](../backend/README.md)。另开终端，在 `frontend/` 目录执行：

```powershell
npm.cmd ci
npm.cmd run dev:h5
```

浏览器访问 `http://127.0.0.1:5173/`。PowerShell 若允许 `npm` 脚本，也可将 `npm.cmd` 写作 `npm`。Vite 将同源 `/health` 和 `/api` 请求代理至本机 Flask；请不要把浏览器请求直接改为跨域的 `:5000` 地址。检查类型与发布构建分别运行 `npm.cmd run typecheck`、`npm.cmd run build:h5`，构建输出在 `dist/build/h5/`。

页面在同一 URL 下用 `?view=invoices`、`?view=ingredients`、`?view=ingredients&tab=prices&food_item=123` 或 `?view=review&invoice=123` 恢复视图；ID 只接受正整数。默认首页有「上传单据」「单据库」「食材」三个入口：上传单据直接打开系统文件选择器，选完自动上传并进入新单据审核页；单据库进入列表。食材页内有「食材」「价格」标签，各业务页左上角可返回首页。旧的 `?view=prices` 链接仍进入食材页价格标签。浏览器前进、后退和刷新保留已选视图。App 系统返回键尚待平台适配与真机验证。

## 价格历史与箱规（F19）

食材页的「价格」标签用食材建议选择器选定食材，逐条列出采购原值和后端返回的换算状态。可换算价格保留服务端的四位小数精度；缺箱规、未知单位、量纲不兼容分别说明处理办法，空价显示短横，0 元赠品仍显示 0。多币种只逐条列示，可显式按币种筛选。`excluded` 和 `notes` 跟价格显示。

待补箱规按后端顺序显示，可从该组预填表单；原始描述候选必须勾选人工确认后才提交。保存前显示当前可见的**至少**影响条数，保存后显示后端返回的实际 `affected_purchase_count`，并刷新历史价格。来源留空代表不限来源，精确来源的箱规优先。已保存箱规可修改或删除；删除结果显示后端 `message` 原文。食材新增与编辑的基础单位改从 `/api/prices/units` 按量纲读取，不把包装单位混进基础单位。

## 月度、来源与提醒（F20）

价格页新增「月度均价」「来源比价」「涨价提醒」三个视图。月度卡片按服务端 `months[]` 展示加权均价和参与计算的采购记录 ID；折线遇到空月即断开，不将缺失价格画作 0。本期与基期的实际日期和天数紧跟均价，缺任一期数据或基期为 0 时显示原因，不编造涨幅。来源列表保留服务端的低到高顺序，展示原始描述与箱规供人工判断可比性；只有一个来源时不展示差价。

提醒按食材和币种分组，提供持久的启用开关与阈值，以及只影响本次查询的临时阈值。达到阈值与「无法比较」分开列示；统计的 `excluded`、`notes` 与数字一同显示。多币种统计须显式选币种，界面不混算；接口失败或统计触顶显示服务端错误原文。

F01 的布局截图在 [docs/f01](docs/f01/)：桌面单据、桌面审核、手机审核、桌面与手机食材。截图记录的是当时的布局占位；当前食材页面显示后端数据。

## 食材读路径（F02）

进入「食材」后读取 `GET /api/categories` 和 `GET /api/food-items`。关键词按后端基础搜索匹配英文名、中文名与规格；分类筛选与关键词组合传给后端。每页 20 条，「加载更多」沿用服务端 `offset`，切换关键词或分类时从首条重新查询。点击食材会通过 `GET /api/food-items/{id}` 打开详情。加载中、无结果、请求失败分别显示不同提示；失败后可重试。

## 食材维护与选择器（F03）

「新增食材」与详情中的「编辑食材」共用最短表单：英文名、分类、基础单位必填，中文名与规格在「更多信息」中。重复名称返回 409 时，字段旁显示服务端原因，并提供「打开已有食材」。详情中的删除需要再次确认；被采购记录或单据引用时，服务端拒绝删除，页面保留详情和错误原因。

「分类管理」是食材页的次级入口，可新增、改名、删除分类；仍被食材引用时显示食材数量和处理办法。分类修改成功后重新读取分类与食材列表。「选择食材」打开独立的 `IngredientPicker.vue`，支持搜索和加载更多；组件只在用户点击某条结果的「选择」后发出该食材 ID，供后续审核行复用。当前页面只展示选择结果，不改动任何记录。

## 食材合并与孤立食材筛选（F18）

食材详情的「合并重复食材」固定当前食材为保留项，可搜索并选择最多 10 条被并入项。先预览服务端给出的采购记录、发票行、箱规搬动数量与冲突；确认按钮旁显示「合并不可逆」。有箱规或单位冲突时按钮禁用，页面显示服务端原因及涉及的食材、单位或箱规 ID。执行成功后显示实际搬动数量，并重新读取食材列表和详情。合并没有撤销入口。

列表的「从没买过」使用 `GET /api/food-items?never_purchased=true`，可与关键词和分类一起筛选。已作废采购记录仍算买过；草稿行可能引用筛出的食材，因此筛选结果不保证可删除，删除收到 409 时仍显示服务端原因。

## 单据读路径与单据头（F04）

「单据库」`GET /api/invoices?completed=false` 显示待办，切换「已完成」改用 `completed=true`；每页 20 条，上一页/下一页使用服务端 `offset`。卡片显示来源、日期、状态以及待核对/已入账/已跳过行数。点击卡片通过 `GET /api/invoices/{id}` 查看单据头、原件文件清单和行状态。空字段显示「待填」，没有行时不伪造进度。加载中、空列表、请求失败分别提示。

单据头可修改来源、单号、日期、币种和总额；清空字段会提交 `null`。金额作为字符串提交，不经 JavaScript 浮点转换。保存后再次 `GET` 回读服务端值。已确认行的历史采购值不会随着单据头修改而回溯，编辑区会提示这一点。浏览器刷新 `?view=review&invoice=<id>` 会重新读取同一单据。行草稿编辑见下面的 F07 一节；整单对账与「完成单据」见 F09。

**未保存就离开会先问。** 单据头编辑中改过值、上传队列里有没传完的文件、上传正在进行时，切换一级入口、返回列表、浏览器前进/后退都会先弹确认；选择「仍要离开」才丢弃，选择「留在本页」会把视图和输入留在原处。刷新或关闭标签页由浏览器自己的 `beforeunload` 提示。这些逻辑集中在 `src/shared/platform/leaveGuard.ts`，业务组件只注册「我现在有未保存的内容，原因是什么」。

## 文件上传与识别任务（F05）

「上传单据」提供三个入口：**拍照**（`uni.chooseImage` + `sourceType: ['camera']`，手机浏览器直接调相机）、**相册 / 图片**、**PDF / 图片文件**（`uni.chooseFile`）。另有开关「只保存文件，手工录入」——只存原件、不启动识别。表格（CSV / XLSX）从列表的「导入表格 / 导出明细」进入。

上传按第 4.1 节的顺序发请求，这是产品决定而不是实现方便：

1. 第一个文件 `POST /api/invoices` 且带 `recognize=false`；
2. 其余文件逐个 `POST /api/invoices/{id}/files`；
3. **全部页都存好之后**，非手工路径才 `POST /api/invoices/{id}/extraction`。

用 `recognize=true` 直接上传会让后端在第 2 页还没传完时就开始识别第 1 页——模型读了两页单据里的一页，而界面上没有任何地方会说出这件事。

选择之后、上传之前可以看到文件名、大小、页序，并用「上移 / 下移 / 移除」调整顺序；页序就是列表顺序。不支持的扩展名、空文件、超过 20 MB 的文件在本地就被拦住并说明原因，但**真正的上限由服务端决定**（`UPLOAD_MAX_BYTES`，默认 20 MB，整次请求是它的 4 倍）：服务端拒绝时照它的原文显示。超大的上传常常表现为连接被断开而收不到 413 响应，这种情况的文案会同时写出两种可能的原因，不单方面说成「后端没启动」。完全相同的文件返回 409，页面照服务端原文提示它已经在哪张单据上；跳过去打开那张单据属于 F10。

中途失败不丢已传的页：提示会写明「单据 #N 已经建立、前 K 页已保存、识别没有启动」，并给出「重试剩下的页」和「打开这张单据」。在详情里「补传文件」可以继续传，补齐后由用户点「开始识别」。上传进度是 `uni.uploadFile` 的真实字节进度，不是估算；上传中可以「中断上传」，已保存的页仍留在单据上。

详情里的「识别任务」卡片读 `GET /api/invoices/{id}/extraction`，显示 `排队中 / 识别中 / 已完成（产出 N 行）/ 失败（原因）`。任务状态在后端持久化，所以**离开这张单据时轮询会停**，回来重新查询；任务结束后自动重读单据，草稿行随之出现。**不显示伪造的百分比**——后端给的是状态与页数，用它编一个进度条就是编数字。provider、models、`prompt_sha12`、`doc_class`、错误码和后端的全部警告收在「诊断详情」里。Fake 识别器的结果一律带「演示识别结果」标识。HEIC 可以上传保存，页面会说明预览与识别能力取决于后端和浏览器当前的支持情况，不替它们承诺。

文件选择与上传隔离在 `src/shared/platform/filePicker.ts` 与 `upload.ts`。两处 App 待办写在代码里：`uni.chooseFile` **没有 App 实现**（App 端调用会得到一句明确的错误，而不是静默失败），`uni.uploadFile` 在 App 端走 `filePath` 而不是 `File` 对象。

## 原件预览与字段证据（F06）

单据详情变成**审核布局**：桌面左边原件约 45%、右边单据头/行/证据约 55%，两侧各自滚动，切换行不会把原件滚回顶部；窄屏是「原件 / 填写」两个标签，**两块都留在 DOM 里**（`v-show`），所以来回切换保留当前行、文件、页码、缩放和滚动位置。布局用的是 JS 测到的视口宽度（`src/shared/platform/viewport.ts`），不是 CSS 媒体查询单独判断——两边各自判断会在断点附近打架，表现是桌面上少了一块。

**原件**读 `GET /api/invoices/{id}/files/{file_id}/content`，拿到的是**存进去的原始字节**，页面只做缩放，不重新编码。多个文件有文件标签，PDF 有翻页，缩放是 1× / 1.5× / 2× / 3× / 4×（PDF 会按倍数重新渲染保持清晰，图片用 CSS 放大）。选中某一行时，按它证据里的 `file_id` 与 `page` 自动跳到对应的文件和页。

**字段证据**按 `raw_fields` 显示五个字段的原文、识别状态（识别出内容 / 这一格认不出 / 单据上没有这一格）、各模型读法与交叉裁决结论。点字段才去取 `GET .../lines/{line_id}/crop?field=...` 的原图小块，并且：

- **后端记了坐标**（`raw_fields.fields.<字段>.box` 非空）才自动请求，**不带** `row` / `column`；
- `box_source=grid_row` 的裁图标成「**整行参考**」，明说只锚定到行、没有定位到列；
- **没有坐标就不请求**，写明「这一页没有建立行号锚定，系统不会替你猜是哪一格——请在左侧原件上核对」。页面上有「自己指定格子」，用户显式选了行带与列带之后才带 `row` / `column` 请求，并标注「这是你指定的格子……不是系统判断的位置」。猜一个 `row` 会让后端返回 200 和**相邻那一行**的字迹，这是唯一一种不报错的错；
- 裁图失败（含 404）照服务端原文显示，并说明已回退到整页原件，不显示可能错行的图片。

手工加的行没有识别证据，直接说明；表格导入的行给单元格坐标，不给原图小块（`.csv` 里没有像素）。`recognition.is_fake` 为真时原件区和证据卡都带「演示识别结果」。

**HEIC 按浏览器实际能力提示**：页面真的去解一次，解不开就说「这个浏览器解不开 HEIC……原件已经完整保存在服务端，不受影响」。有意思的是**裁图仍然能看**——后端有 `pillow-heif`，裁出来的是 PNG。

### `shared/platform/documentPreview.ts` 的边界

文件字节→可显示内容的全部浏览器 API 都在这一个文件里：`URL.createObjectURL`、`Image` 解码探测、`<canvas>` 与 pdf.js。业务组件只见到 `RenderedPage` 与 `PdfDocument`。App 端待适配的四件事写在该文件开头的表里：图片要先 `uni.saveFile` 成本地临时文件、HEIC 看系统、PDF 渲染要换平台组件或原生插件、页数同理。非 H5 分支现在抛的是一句说明缺哪项能力的错误，不是静默空白。

⚠️ **pdf.js 必须用静态 import**。`uni build -p h5`（`vite-plugin-uni` 3.0.0-alpha-5030620261106001）会把 `await import('pdfjs-dist')` 编译成裸标识符 `import("..-node_modules-pdfjs-dist-build-pdf.<hash>.js")`，而且**那个 chunk 根本没生成**：`npm run dev:h5` 一切正常，`npm run build:h5` 出来的页面直接报 `Failed to resolve module specifier`。两个 `#ifdef H5` 块负责把 pdf.js 挡在非 H5 构建之外，这正是当初想用动态 import 达到的效果。pdf.js 4.10 面向当代浏览器（用到 `Promise.withResolvers`，Chrome 119+ / Safari 17.4+）；要更宽的基线就换 `pdfjs-dist/legacy`。

## 审核草稿编辑、手工加行与食材匹配（F07）

选中一行后，审核面板里出现这一行的**草稿表单**（`src/features/invoices/LineEditor.vue`）：商品名称、数量、采购单位、单价、行金额；日期 / 来源 / 币种折在「按需覆盖」里，默认继承单据头，表单直接写出继承来的是哪个值。当前界面只录入采购行，不显示行类型切换。表单下面是**食材匹配**（`FoodItemMatcher.vue`），再下面才是 F06 的字段证据——先填，再对着左边的原件核。

2026-11-17 的审核界面调整：标题与低频操作收在同一行，原件和填写区靠近视口顶部。草稿表单将「原始描述」显示为「商品名称」；可用的识别值以灰色候选放在对应空框内，未识别出的格子保持空白。一次只在当前待核对字段下显示「此数据正确 / 修改」，其他候选只在字段名旁标「AI 识别 · 待核对」；点击其输入框即可切换核对按钮。确认后候选成为可编辑的黑色表单值；修改会清掉候选并将焦点移入该框。两模型文字不一致时，候选按纯英文、纯中文、含数字或符号排序，同档取文字较多者；数字不一致时不猜。原来的两模型原文折叠区已从审核页移除。

四条规则是契约，不是样式偏好，都写在 `lineDraft.ts` 的注释里：

- **数值全程是字符串。** 输入、比较、提交都不经 `Number()`，也不在前端做乘除。后端的 `parse_decimal` 直接拒绝 JSON 小数，理由不是洁癖：`JSON.parse` 在任何代码读到之前就已经把 `1234567.89` 过了一遍 double。
- **空格子就是 `null`，不是 0。** 后端对认不出的格子刻意留空，而 0 在这个产品里是「赠品 / 0 元行」这种确定的含义。表单因此把两种状态分开标：空的写「未知（空）」，填了 0 的写「**这里的值是 0，不是「未知」**」。
- **PATCH 只带改过的字段，并且一定带 `version`。** 后端把「没出现的键」当成「保持原值」、把显式 `null` 当成「设为未知」；整表提交会让一份过期的表单覆盖掉别人刚改的值。`version` 省掉的话 `_check_version` 会跳过检查，于是每次保存都变成盲目覆盖。
- **候选永远只是候选。** 行自带的 `match_candidates`、`/api/invoices/{id}/supplier-candidates`、`/api/invoices/match?description=` 和 F03 的食材选择器，四个来源都只列出候选，**必须用户点一下**才会写 `food_item_id`。手写件的商品名本来就不该靠 OCR——中文商品名跨模型分歧率 96.0%，所以那条路走供应商历史：老板认的是自己的货，不是认字。

**本地校验照后端的规则写**（小数位 4/4/2、整数部分 12 位、采购行不能负数、采购行数量必须大于 0），目的是把错误提示放在字段旁边而不是等一次往返。它只会比后端更严，不会放宽；后端拒绝的一律照原文显示。

**版本冲突（409）**会重新读这张单据，然后把「你的输入 / 服务端现在的值」逐字段摆出来，给两个出口：「用服务端的值（丢弃我的输入）」和「保留我的输入，按新版本重新保存」。页面**不替用户合并**——两个数字都可能看起来成立，选错了不会报错。

**切行前会先问。** 这一行有没保存的修改时，点另一行会弹出「第 N 行改了 X，还没有保存」，只有「放弃修改」才切过去；整页离开（切一级入口、返回列表、刷新）沿用 `leaveGuard.ts`。

**加一行**：行状态概览右上角的「加一行」`POST .../lines`，所有格子先留空，加完自动选中，然后逐格填。手工加的行（`raw_fields` 为空）可以删；识别出来的行不能删——删掉就和原件对不上了，那种情况要标成「跳过」。

**首次采购自动建食材（2026-11-17 调整）**：审核页不再有新建食材表单。现有食材可照常搜索选用；没有同名食材时只选分类，可在分类列表里就地新建。确认这一行时带 `new_food_item: {name, category_id, use_purchase_unit_as_base:true}`，后端从已保存的本行采购单位取首个单位，并在同一事务内建食材、入账；入账失败不会留下孤立食材。同名已有食材复用，不再建重复项。包装单位可作为首次单位保留，但无箱规时不生成标准化单价，之后可在食材页修改单位。已完成单据和草稿单据都可在列表标题旁重命名；改的是单据来源名称，既有采购记录的来源不会回写。

**`review_issues` 是对象数组，不是字符串数组**（`types.ts` 里原来的 `string[]` 在 F07 改掉了）。它来自 `invoice_lines.review_metadata["issues"]`，识别写的是 `field` / `code` / `raw_text` / `message`，表格导入还会加 `sheet` / `row` / `column` / `cell`。只要还剩一条，后端就拒绝确认这一行；而它只在**它自己指的那个字段被 PATCH** 之后才消失，所以每条提示就显示在那个字段旁边。

**已入账的行是只读的**：后端拒绝 PATCH 一个已确认的行，因为它的数字已经进了采购历史，原地改草稿只会让两处对不上。页面照这个口径说明，并提供「撤销确认」入口。

## 逐行状态与入账（F08）

「确认此行并入账」先保存该行尚未提交的修改，用 PATCH 返回的新 `version` 只确认这一行。确认请求显式传 `line_id`、`version` 和用户选定的 `food_item_id`。HTTP 200 仍逐条检查 `results[].ok/error`，失败会留在当前行并显示原因。金额不符时直接展示服务端返回的纸面金额、数量乘单价、差额与容差；用户点「仍按行金额入账」才带 `accept_amount_mismatch:true` 重试。金额不经前端浮点计算。

「跳过此行」必须输入原因，带 `version` PATCH 成 `skipped`；可改回待核对。已入账行的「更多操作：撤销确认」先告知原采购记录会作废，用户确认后带 `version` 调 `POST .../unconfirm`。每次状态变化从服务端更新整张单据，行计数与详情同步；「重新读取详情」可随时重查。重复确认由按钮忙碌状态与后端唯一约束双重阻止，不会多记一笔采购。

## 对账与收口（F09）

详情的「对账与漏行检查」直接显示服务端的文件数、行数、总额、已入账金额和差额。仍有待核对行、没有总额、混合币种、缺币种或币种不符时说明无法对账，不把未知差额写成 0；差额过大时提示核对，但不阻止完成。至少一行且没有待核对行才可打开收口面板。打开面板会重新读取详情；对照原件后须勾选「我已检查原件有无漏行」，才能提交 `POST /api/invoices/{id}/complete`。完成后自动切到已完成列表，单据详情仍可回看原件与已入账行。服务端 409 带 `pending_line_nos` 时会重新读取并定位未处理行。

已完成单据使用「采购回执」视图：页头显示采购来源、日期、单号和单据总额，正文以大字清单展示已入账商品，并单列已跳过的行；原件通过「查看原件」打开。每条已入账行根据 `purchase_id` 读取 `GET /api/purchases/{id}`，显示当前采购记录，避免采购记录修订后继续展示过期的审核草稿。采购记录读取失败时该行不显示草稿金额，提供重试。底部的入账金额和差额明确标为**完成时**服务端对账结果；如采购记录后来修订或作废，回执会提示两者口径不同。金额和数量仍全程保留字符串，不在前端计算合计。

单据币种默认 USD，无需手动填写；审核时可在单据信息里改为 CNY，已完成回执的总额下方也可修改。已完成单据的币种修改只更改单据头，已入账采购记录不会自动换算或改币种，对账结果会随服务端响应更新。表格导入的整批币种预选 USD，可在预览前更改；表格中逐行明确写出的币种仍按行处理。已完成旧单据若未存币种，回执按 USD 默认值显示，原始记录本身不被自动改写。

## 异常恢复与低频操作（F10）

上传完全相同文件返回 409 时，上传面板可根据 `details.invoice_id` 打开已有单据；详情中的 `possible_duplicate_invoice_ids` 是提醒，可点开核对，不阻断审核。单据详情的「单据更多操作」提供重新提取、删除拍坏文件和删除整单。重新提取会提示核对未确认草稿；运行中的任务与已入账行由后端 409 拦截。删最后一个原件、删正在识别的原件也由后端拦截。删除整单先确认；若有已入账行，再显示行数并要求二次确认。服务端核对当前行 ID，一次事务内作废其采购记录、保留修改日志，再作废单据并删除原件；已作废记录不再计入价格统计。同一文件之后可重新上传。已入账的历史数值不能通过草稿修改；当前界面尚无采购记录编辑页，需通过 `PATCH /api/purchases/{id}` 修正并保留修改日志，或撤销该行确认后重新审核。

## 表格导入与采购明细导出（F11）

在单据列表点「导入表格 / 导出明细」。选择 CSV/XLSX 后先设置工作表、表头行、列映射、编码、分隔符、数字与日期规则，再点「预览表格」。预览显示原始行号、解析值和每个异常，不写入单据。修改设置会使预览失效，须重新预览；用户确认映射与格式后才能创建。若仍有异常，须明确选择「在审核中逐行手工处理」，这些行仍不能直接确认，须在现有审核表单修正。创建后直接进入同一单据审核视图，表格原件可下载。

同一文件重复创建收到 409 后，可打开原批次；修改文件后重传会建新批次，不覆盖旧记录。导入时“行类型”列会被忽略，所有新行按采购处理。导出可选 CSV 或 XLSX，下载的是服务端返回的原始附件；默认仅有已入账采购行，不含待核对、调整行或作废记录，请求不带分页参数。App 端表格选择和下载尚待独立适配。

## Web 集成验收（F12）

在隔离 SQLite、`OCR_PROVIDER=fake` 的本地 Flask 与 Vite 同源代理上，用 Chrome 157 实际点击了 1280px 桌面和 390px 窄屏两条完整流程：新增食材、上传单据、确认两行（第二行随确认新建食材）、手工补第三行并保留待办、离开并刷新后返回、跳过第三行、完成单据、从已完成列表回看原件。Fake 识别器只生成两行，第三行通过页面的「手工加一行」补齐；界面始终标明「演示识别结果」。还在窄屏完成了 CSV 只读预览和创建，预览前后待办数不变。43 行单据在 390px 与 1280px 均无横向溢出；桌面填写区可独立滚动。另用两页合成 PDF 验证 H5 原件预览和翻页。

断网时重新读取会保留上次内容并显示失败原因；网络恢复后再点「重新读取详情」，旧错误会消失。服务端将 `UPLOAD_MAX_BYTES` 临时设为 4096 字节时，用 574 KB 图片从页面上传实际收到 HTTP 413，页面给出缩小文件的办法且未新建单据。输入框键盘焦点、Tab/Enter 主导航和空格操作收口勾选、主要文字组合的对比度、可见点击宿主的 44×44 CSS px 目标已在浏览器检查。H5 的 `uni-button` 键盘适配集中在 `src/shared/platform/keyboardButtons.ts`。此验收使用 Fake OCR；**真实 OCR 的识别效果不由本轮 Web 验收背书**。

浏览器联调发现后端在更换一行的 `food_item_id` 后，PATCH 响应仍可能带旧的 `food_item` 对象，而下一次 GET 已是新选择。前端因此在选择或取消食材的 PATCH 成功后重读单据，再显示选中项并允许确认。生产构建通过本地预览服务实测可打开两页 PDF、翻到第 2 页。

**App 真机适配清单（均未验收）**：拍照与相册权限及返回文件、PDF/表格文件选择、图片与 PDF 原件预览、表格附件下载、系统返回键和未保存提示、手机到后端的可达地址与认证及传输保护。H5 的 390px 浏览器结果不等于 App 真机结果。

## OCR 配置

后端默认 `OCR_PROVIDER=fake`：识别结果是演示数据，响应的 `recognition.is_fake` 会标出这一点。真实 OCR 需在后端本机环境中配置 `OCR_PROVIDER=dashscope`、`OCR_API_KEY`（或 `DASHSCOPE_API_KEY`）及 `OCR_BASE_URL`（或 `DASHSCOPE_BASE_URL`）；详见后端 README 的配置说明。没有真实凭据时使用 Fake 模式即可验证 F00。前端没有 OCR 密钥，也不复制后端 `.env`。

## API 基座

`src/shared/api/request.ts` 统一走 `uni.request` 和同源路径；HTTP 失败按后端的 `error.code/message/details` 解析，网络失败单独提示。`src/shared/api/types.ts` 中的金额、数量使用 `string | null`，不转换成 JavaScript `Number`。分类响应为 `{items}`；食材和单据列表为 `{items,total,limit,offset}`；提取任务为 `{items,total}`。multipart 上传走 `src/shared/platform/upload.ts`（字段名 `files`，一次一个文件）；二进制原件与裁图走 `apiRequestBinary`（`responseType: 'arraybuffer'`），裁图的证据在响应头 `X-Field` / `X-Page` / `X-Model-Values` / `X-Agreement` 里，失败时把字节当 UTF-8 JSON 解出来读服务端的 `error.code/message/details`。

⚠️ **uni-app 的一个坑记在这里**：`uni.uploadFile` 在 `@dcloudio/uni-h5@3.0.0-alpha-5030620261106001` 里，只要 `files` 不是数组就执行 `if (!filePath) reject('file error')`，**然后照样把请求发出去**——于是服务端收到并保存了文件，而调用方收到的是失败。传 `File` 对象必须用 `files: [{ name, file }]` 这种写法，`upload.ts` 的注释里也写了这件事。
